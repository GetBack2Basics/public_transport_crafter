2. System Architecture & Zero-Mock Standard

The platform enforces a strict Zero-Mock Standard: all calculations, coordinates, timetable departures, and Opal passenger patronage figures are derived directly from genuine Transport for NSW open data feeds. Synthetic arrays and simulated fallback schedules are prohibited by automated AST scanners.

5. Command-Line Interface (CLI) Execution & Tests

Execute automated batch query optimization and test suites from PowerShell or bash: 

# Run Natural Language Query Orchestration
python -m src.Orchestration.query_orchestrator \
  --query "With the same number of buses and trains, how can the route from Maitland to Newcastle University be optimized?" \
  --clean-local

# Run All 31 Anti-Mock & GCS Integration Tests
.venv\Scripts\pytest -v
# Deploy Web Portals and Documentation to Google Cloud Storage
python scripts/deploy_portal_to_gcs.py

6. Frequently Asked Questions (FAQ)

Why does the system run with zero idle compute costs? ▼
The web interfaces are compiled as client-side applications executing in the user's browser. Data artifacts are stored as static JSON and Parquet objects in Google Cloud Storage with global CDN edge caching. No dedicated server or container needs to run while idle.
How does the system ensure zero added fleet budget? ▼
The mathematical solver enforces a hard Peak Vehicle Requirement (PVR) constraint: ∑ Vehicles(opt) ≤ ∑ Vehicles(base). Departure shifts only rearrange vehicle start times to align with connecting train or ferry arrivals; total vehicle service hours and driver shift duty hours remain strictly invariant.
Can I inspect routes not shown in the quick scenario chips? ▼
Yes. The system indexes all 10,266 routes operating across New South Wales. Enter any route number (e.g., 880, 333, B1, T1, 275) into the search bar in the Planning Portal or the Data QA Hub to load that corridor's live road-following geometry and schedule.
